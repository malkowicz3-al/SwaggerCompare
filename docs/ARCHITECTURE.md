# SwaggerCompare: architecture

Windows desktop app. Electron, Monaco diff editor, `yaml` parser. esbuild bundles the renderer into one classic script (ADR 0003); no UI framework, no preload. The same static files also run from file:// in an Edge app window (`SwaggerCompare.bat`).

## Files

```
package.json            "type": "module", scripts, electron-builder config ("build" key)
main.js                 app:// protocol handler, BrowserWindow + security settings, blocks navigation
src/index.html          CSP, Monaco AMD loader, bundled renderer, layout (title bar, pane headers, editor, change list); relative paths only
src/style.css
src/icon.svg            app logo (favicon, README); src/icon.png (256 px, window icon), build/icon.ico (exe icon)
src/renderer.js         Monaco setup, drag&drop/open/clear/swap, live compare (300 ms debounce), title/version bar, grouped list (objects or endpoints), filters, tag bar, F8 navigation, highlight + name flash of the selected change in both editors, Copy report
src/report.js           ES module, pure, no DOM: heading(meta), summary(changes), byEndpoint(changes), markdown(res)
src/gen/renderer.js     esbuild output (committed): renderer + compare + report + yaml as one IIFE
vendor/                 Monaco core + YAML highlighting and used font weights, copied from node_modules by scripts/vendor.mjs (committed)
scripts/build-web.mjs   builds dist/SwaggerCompare-web.zip with the repo-root layout (bat, src/, vendor/)
SwaggerCompare.bat      opens src/index.html in `msedge --app`, falls back to the default browser; CRLF, `-text` in .gitattributes
src/compare.js          ES module, pure, no DOM: compare(leftText, rightText) -> result (see below)
test/compare.test.js    node:test + node:assert; test/report.test.js for report.js
test/fixtures/          swagger2-old.yaml, swagger2-new.yaml, openapi3-old.yaml, openapi3-new.json
```

## Dependencies (exact versions pinned)

- dependencies: `monaco-editor@0.52.2` (last version where the AMD `min/vs` build is supported, see ADR 0002), `yaml@2` (exact 2.x).
- devDependencies: `electron` (current stable), `electron-builder`.
- Nothing else. Tests use `node --test`. The zip step uses PowerShell `Compress-Archive`.

## Data flow

1. The user pastes text or drops a file onto a pane. A capture-phase `drop` handler on each pane reads it with `file.text()` and calls `model.setValue()`. The document also gets `dragover`/`drop` `preventDefault`, so a drop outside a pane never navigates the window.
2. Monaco `createDiffEditor` with `originalEditable: true` and `renderSideBySide: true`. Monaco computes the text diff and colors it live. The text is never reformatted.
3. Live compare: 300 ms after any edit, `compare(original.getValue(), modified.getValue())` runs (no button). Parse errors never move the cursor; list scroll and selection survive re-runs.
   - Both sides are always parsed. `meta = { left, right }`, each `{ title, version, spec }` (strings or undefined, from `info.title`, `info.version`, `openapi`/`swagger`) or `null` for a side that didn't parse.
   - If either side fails to parse: `{ error: { side: 'left'|'right', line, message }, meta }` (the left error wins). The UI shows the message and no list.
   - Otherwise: `{ changes: [{ kind: 'added'|'removed'|'changed', tag, text, where, path: string[], side: 'left'|'right', line, left, right, details?: string[], affects, breaking, flash }], meta }`. `affects` is `[{ endpoint: 'GET /x', via?, dir: 'request'|'response'|'endpoint' }]` (see Usage below; `[]` means "Other"), `breaking` is a boolean (see Breaking below), `flash` is `{ left?, right? }`, each `{ line, from, to }` (1-based Monaco columns, `to` exclusive) of the changed node's name on a side where the path exists exactly. `left`/`right` are `{ start, end, exact }` lines of the affected fragment on each side; `exact: false` means the path is missing there and `start === end` is the nearest existing ancestor's line. `text` is short ("Added property phone (string)"), `where` names the object it belongs to ("GET /users", "User", "User.address", "schemas", "parameter Limit"), `path` is the full path. `tag` is a one-word category: explicit for structural entries (`endpoint`, `response`, `schema`, `parameter`, `property`, `required`, `type`, `refactor` for $ref extraction/inlining and composition refactors), otherwise the last non-numeric path segment (`enum.2` -> `enum`, `info.version` -> `version`).
4. Title bar and pane headers: `#versions` in the title bar centre shows `heading(meta)` ("Orders API  1.4.0 → 2.0.0", both titles if they differ, hidden when empty). Each pane header shows "Original" / "Modified" with the file name (or "Pasted text") as muted text next to it, and a second line "title · v1.4.0" when the spec has a title. The renderer keeps the last good meta per side: a side that doesn't parse (`meta[side] === null`) keeps its previous title while the user types; an empty side, a newly opened or dropped file and Clear reset it, and Swap moves it along. A leading `v` of the version is not doubled ("v1.4.0"); a spec with a version but no title shows just the version. When only one side has text, `compare()` still runs (the empty side is an error) just to read the other side's meta.
5. Under the Changes header a second row holds an `Objects | Endpoints` toggle (`aria-pressed`), the `⚠ Breaking N` filter chip and `Copy report`; below it the `summary(changes)` line ("Endpoints: 1 added · 2 removed · 3 changed · Schemas: 2 changed · ⚠ 5 breaking"; endpoints "changed" include those hit through schemas).
   - Objects view: the list groups entries by `where` (first-appearance order). A group whose entries are component changes shows "Used in: GET /orders, POST /orders (+n)" (the `affects` endpoints that have a `via`, deduplicated, at most 4).
   - Endpoints view: rows come from `byEndpoint(changes)`: one group per endpoint in first-seen order, "Other" (changes with no `affects`) last. A schema change appears under every endpoint it hits, its text prefixed with the `via` ("request body › currency: now required"). The counter and F8 walk rows; the total, the kind chips and the summary count unique changes. Details toggles get one id per row. The selection is remembered as (group, change): a re-run restores that row, or the change's first row when the group is gone (e.g. after switching views), and opens its group.
   - Copy report: `markdown(res)` gives `# heading`, the summary, a `## Breaking` list, one `## <endpoint>` section per group (details as a nested list, ⚠ on breaking rows), then `## Other`. It is written with `navigator.clipboard.writeText`; if that is missing or refused (some file:// windows), a hidden `textarea` + `document.execCommand('copy')` is used. The button shows "Copied" (or "Copy failed") for 1.5 s.
6. Each group is a `li.group` with a header button (chevron, `where` with a leading HTTP method as a pill, count of visible entries, coloured +a −r ~c, distinct tags below) and an `ol` of entries. Groups start collapsed; expanded ones are remembered by `where` in `open` across re-runs (one set for both views), and any active filter (kind chips, Breaking chip, tag bar, search) expands every matching group. A Collapse all / Expand all button at the right end of the tag bar expands every group if all are collapsed, otherwise collapses them; it is disabled while filtering. Breaking entries get a `⚠` marker (`role="img"`, label "Breaking") and the `breaking` class; the search also matches "breaking", the affected endpoints and `via`. The tag bar under the header has one chip per tag ("property **5**", sorted by count); pressed chips restrict the list to those tags. Navigation: ↑/↓ inside the list walk visible headers and entries; the ▲/▼ buttons and F8 / Shift+F8 step through visible entries (wrapping, opening the entry's group) and the header shows "3 / 17". F8 is caught by a capture-phase `keydown` listener on `document`, which runs before Monaco's own F8 (next marker) handler on the editor node. Each entry renders `kind`, `tag` (a small chip), `text` and `details` as an indented sub-list behind a collapsed "Details (n)" toggle (a sibling button; it only toggles, open state survives live re-runs). The tooltip shows `path.join(' › ')` and side/line; the search also matches `tag`, `where`, `path` and `details`. A click on an item (or ↑/↓, F8) sets the cursor on `line` in the original editor (side `left`, for removals) or the modified editor (side `right`, for added/changed items) and highlights the change in both editors with a decorations collection per editor: an exact range as whole-line `hl` background plus an `hl-bar` gutter bar, an inexact one (fragment missing on that side) as a dashed `hl-anchor` line at the nearest ancestor. Only the primary side (`side`) is revealed (`revealLinesInCenterIfOutsideViewport`, or `revealLineNearTop` of its first line when the fragment is taller than the viewport); the other editor follows through the diff editor's synced scroll. Each re-run clears the highlight; a restored selection is re-highlighted without scrolling.
   Name flash: a second decorations collection per editor marks `flash.left`/`flash.right` with `inlineClassName: 'name-flash'` (a 1.5 s CSS fade from the focus colour; a static mark under `prefers-reduced-motion`). It is applied only when the change is revealed (click, ↑/↓, F8, the ▲/▼ buttons), never on a restore after typing, and removed by a 1.6 s timeout and by `clearHl`.

## compare.js internals

- `parseDocument(text, { lineCounter })` parses each side. YAML 1.2 is a superset of JSON, so one code path handles both. The first `doc.errors[0].linePos[0].line` is the reported error line. Duplicate keys are already errors (uniqueKeys).
- Line index: one walk over the CST nodes (`YAMLMap` pairs, `YAMLSeq` items) builds `Map<pathKey, {start, end, key?}>`, with `pathKey = JSON.stringify(path)`. `key = {line, from, to}` is the node's name: a map key's range (with its quotes in JSON), the `name` value of a sequence item that has one (a parameter), or a scalar item itself (an entry of `required`, `enum`). `emit` looks up `flash` there, after stripping a trailing `$ref`/`allOf`/`oneOf`/`anyOf` segment so a refactor flashes the property name. `start` is the line of `pair.key.range[0]` (a sequence item's `range[0]`); `end` is the line of the value's end offset minus one (not before the key's end), walked back over whitespace so a trailing newline or the blank lines after a `|`/`>` block don't spill onto the next key. A one-line scalar has `start === end`. `line` uses `start`; a lookup that misses goes to the nearest existing ancestor path, so the line is always defined (`rangeOf` then returns that ancestor's first line with `exact: false`).
- The structural diff runs on `doc.toJS()` of both sides. Map keys are compared as sets, so key order produces no entries.
- Recognizers are path-context rules that run before the generic fallback:
  - `paths.<p>.<method>` add/remove: "Added endpoint" (where "POST /users").
  - `parameters` arrays are matched by `in+name`, never by index. They produce add/remove, `required` change and type change (`type` for 2.0, `schema.type` for 3.x). A 2.0 `in: body` param is treated as a parameter.
  - Schemas live under `definitions.*` (2.0) and `components.schemas.*` (3.x). Recognizers: whole schema add/remove; `properties.*` add/remove/type; the `required` array compared as a set ("email: now required" / "no longer required", where "User").
  - `responses.<code>` add/remove.
  - `requestBody` (3.x) is not special-cased. It goes through the generic walk.
  - Generic fallback: any remaining leaf or subtree difference gives "<rest> added", "<rest> removed" or "<rest>: old → new". A recognizer marks the subtree it consumed, and everything else always reaches the fallback, so no difference is lost. A recognizer consumes only the keys it actually reported on (e.g. a type read from `type` leaves a sibling `$ref` to the fallback). Repeated parameter labels are paired in order (`query 'a'#2`), and parameters without `in`/`name` or `$ref` are compared by position.
- `where`/`rest` (locate): inside `paths` where is "METHOD /path" (or the path for path-level keys) and rest drops `properties` segments and shortens `requestBody…schema` → "request body" (`request body (<mime>)` when the schema isn't reached), `responses.<code>…schema` → "response <code>", `parameters.<in:name>.schema` → the parameter name. Under a schema (`definitions.X`, `components.schemas.X`) where is the schema plus nested property names up to the last property, e.g. `User.address` for `User.properties.address.properties.zip`; other components get "parameter X", "response X", …; a whole added/removed component has where = its section ("schemas").
- Other arrays are compared by index. `$ref` strings are compared as plain strings; local `#/…` pointers are resolved only for extraction below.
- $ref extraction: when one side is a pure `{$ref}` and the other an inline object without `$ref` (a property, items, a parameter schema, a whole parameter, a response…), one changed entry is emitted: "requestId: extracted to schema RequestId" or "…: inlined from schema RequestId". Its `details` are the differences between the inline value and the resolved definition ("definition unchanged" if none; "definition not compared (external $ref)" / "(unresolved $ref)" when it can't be resolved). The matching "Added"/"Removed" entry of the target definition is then dropped. An inline parameter and a `$ref` parameter resolving to the same `in`+`name` are paired. Limitation: if the whole section is new (e.g. no `definitions` on the left), its single aggregate entry is not dropped.
- Composition refactors (`compose`, runs right after extraction in `walk`, `walkProps` and on parameter schemas): fires when a schema gains or loses `allOf`/`oneOf`/`anyOf`, switches keyword, or keeps the keyword but changes the set of member `$ref`s. Same keyword and same member `$ref`s → no entry here; the members are walked generically as before. One changed entry, tag `refactor`, line at the keyword (left side if only the original has it): "Order: now allOf [schema Entity + inline]", "Order: allOf flattened", "Order: allOf members changed: + schema X, − schema Y", "Pet: now oneOf [schema Dog, schema Cat]". A refactor entry (this or an extraction) on a whole component gets that component as `where` ("Order", not "schemas"), so it lands in the component's group. Details: for `allOf` (and a 1-member `oneOf`/`anyOf`, which is the member itself) both sides are flattened by `flat()` (local `$ref`s resolved, members merged in order, then the schema's own keys: `properties` merged recursively, `required` unioned, otherwise the later wins; cycle guard on visited refs, at most 32 `$ref` hops, unresolved → `{}`) and the effective schemas are diffed. If either side is a real union (`oneOf`/`anyOf` with 2+ members) there is no single effective schema, so the details are a raw diff of the two values. A member `$ref` to a whole component that exists only on that side drops its "Added/Removed schema X" entry (not for a 2+ member union, whose raw details don't contain the members). Limits: external `$ref`s flatten to nothing; `not`, `discriminator` and nested unions inside members are not interpreted.
- Usage (`usage(data)`, built once per side in `compare()` as `st.useL`/`st.useR`): `Map<componentKey, [{endpoint, via, dir}]>`, `componentKey = JSON.stringify(['components','schemas','Order'])` (or `['definitions','Order']`, `['parameters','Limit']`…). For every `paths.<p>.<method>`, path-level plus operation `parameters` (`via 'parameter <name>'`, request; a `$ref` parameter is named after its target; a 2.0 `in: body` parameter is request too), `requestBody` (`via 'request body'`, request) and `responses.<code>` (`via 'response <code>'`, response) are searched deeply for local `$ref`s. A ref into a sub-path (`#/definitions/W/properties/id`) counts as a use of `W`. Refs are followed transitively through components with a `seen` set (cycles terminate); each component's direct refs and its transitive closure are memoised, and entries are deduplicated per component by `endpoint|via`. Limits: external refs, callbacks, links and `security` are not followed; it is recomputed on every live re-run (a test keeps 1000 operations sharing a schema chain under 3 s; about 0.5 s today).
- `affects` (`affectsOf` in `emit`): a change under `paths.<p>.<method>` hits that endpoint, `dir` from the segment after the method (`parameters`/`requestBody` → request, `responses` → response, otherwise endpoint); a path-level change hits every method of the path on either side. A change inside a component hits the union of its `useL` and `useR` entries, merged to one entry per (endpoint, dir) with the vias joined ("response 200, 404, 500"), cached per component in `st.affects`. Anything else gets `[]`. `byEndpoint` then gives one row per (endpoint, change), joining the request and response vias. Detail entries of a refactor have no `affects`; `extract`/`compose` pass the refactor's directions to them as `st.dirs`.
- Breaking (`isBreaking(c, dirs, {lv, rv, details})`, `dirs` = the set of `affects[].dir`; an empty set, i.e. an unused component, `info`, `servers`, is never breaking):

  | Change | Breaking? |
  |---|---|
  | Endpoint removed, response code removed, type change, `$ref` retargeted | Yes |
  | New required parameter (`required: true` or `in: path`), request body added with `required: true` | Yes |
  | Content type removed (`…content.<mime>` removed) | Yes |
  | `now required` (or `required: true` set) | In a request |
  | `no longer required` | In a response |
  | Property removed | In a response |
  | Enum narrowed (a value of the left enum missing on the right, or an enum added) | In a request |
  | Enum widened (a new value on the right, or the enum removed) | In a response |
  | Tighter `min*`/`max*`/`pattern` (added, raised minimum, lowered maximum, changed pattern) | In a request |
  | Refactor | If any of its details is breaking |
  | Additions, descriptions, everything else | No |

  A schema used in both directions is breaking if a rule fires for either. Enum entries come from the by-index array walk, so `walk` passes both whole enum arrays down and every entry of one enum is judged on their value sets (an inserted value only widens). Nothing under `example`, `examples`, `default`, an `x-*` key or inside an enum value is judged (those keys are data), unless the segment is a name (after `properties`, `headers`, a components section…). Not judged: `security`, `basePath`, `servers`.
- Output order is depth-first in key order of the modified side; at each level, keys present only on the original side come after the modified side's keys. (JS objects list integer-like keys such as response codes first, in ascending order.)
- For a wholly added/removed path, the endpoint entries (one per HTTP method) cover the path; its other path-level keys produce no separate entries.
- The Monaco diff runs with `ignoreTrimWhitespace: false`, so whitespace changes are shown.

## Electron security

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, no preload. The renderer needs no Node or IPC.
- `will-navigate` and `setWindowOpenHandler` deny all navigation and new windows.
- CSP meta: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; worker-src 'self' blob:; font-src 'self' data:; img-src 'self' data:; object-src 'none'; base-uri 'none'`. No inline scripts. Monaco needs inline styles and data: images.
- The window loads `app://local/src/index.html`. main.js registers the privileged `app` scheme (standard, secure, supportFetchAPI) and serves files from the app root (works inside asar via `net.fetch` of a file URL). Only `src/` and `vendor/` are served; anything else returns 403. Everything is local and nothing comes from a CDN.

## Loading Monaco and yaml

- `index.html` loads `../vendor/monaco/vs/loader.js`, then `gen/renderer.js`. The renderer calls `window.require.config({ paths: { vs } })` with a URL relative to the page, so it resolves under both `app://local/` and `file:///`.
- Workers: under app:// a blob worker `importScripts` `workerMain.js`. Under file:// `getWorkerUrl` throws, and Monaco runs the diff on the main thread.
- `compare.js` and `report.js` stay plain ES modules (`compare.js` imports `yaml`); Node runs them directly in tests, esbuild inlines them (and `yaml`) into the bundle.

## Build and distribution

- `npm run build` runs esbuild and scripts/vendor.mjs; `npm start` builds, then runs `electron .`. All npm packages are devDependencies, since nothing ships from node_modules.
- `npm test` runs `node --test`
- `npm run web` builds and zips `dist/SwaggerCompare-web.zip` (~2 MB), the same layout as the repo root.
- `npm run dist` builds, builds the portable exe, zips it as `SwaggerCompare-win.zip`, then builds the web zip.
- electron-builder config: `win.target: portable`, `artifactName: "SwaggerCompare.exe"`, `win.icon: build/icon.ico`; the BrowserWindow uses `src/icon.png`. `files` is `main.js`, `src/**`, `vendor/**`. asar is on.
- No code signing, no CI, no Linux.
